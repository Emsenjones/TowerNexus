

# Task 004 - Monster Movement

## 1. Overview

This task introduces monster runtime movement for TowerNexus.

This task is designed based on:

- 00_ProjectOverview.md
- 03_MonsterSystem.md

This document only defines the implementation scope of the current task.

## Related Tasks

This task is closely related to:

- Task_001_MonsterDefinition
- Task_002_MonsterWaveSpawner
- Task_003_AStarPathfinding
- Task_005_DynamicPathRecalculation
- Task_007_MonsterDeathAndReward

Relationship:

- MonsterDefinition provides movement speed and animation configuration.
- MonsterWaveSpawner creates runtime monster instances before movement begins.
- AStarPathfinding provides ordered node paths for monsters to follow.
- DynamicPathRecalculation will later update monster paths when map walkability changes.
- MonsterDeathAndReward will later stop movement when monsters die.

This task focuses only on moving spawned monsters along paths generated by the pathfinding system.

This task does NOT include:

- A* pathfinding implementation
- Wave spawning implementation
- Dynamic path recalculation notifications
- Tower placement validation
- Monster death handling
- Player damage handling

These systems are implemented in other tasks.

---

# 2. Goal

Implement runtime monster movement along node paths.

The system should support:

- Monster path assignment
- Movement along ordered NodeBehaviour paths
- Movement from node center to node center
- Current node tracking
- Target node arrival detection
- Basic walk animation triggering

---

# 3. Runtime Architecture

Recommended runtime structure:

| Layer | Responsibility |
|---|---|
| MonsterBehaviour | Stores monster runtime state and movement data |
| AStarPathfindingService | Provides ordered path nodes |
| Map System | Provides NodeBehaviour positions and runtime node data |
| MonsterSpawner | Creates monster instances before movement starts |

MonsterBehaviour should consume path results, but should not calculate A* paths itself.

---

# 4. Movement Rules

Current movement rules:

- Monsters move along node center positions
- Movement is calculated on the XZ ground plane
- Y position should remain stable according to monster prefab placement
- Monsters follow an ordered list of NodeBehaviour nodes
- Monsters move from current node to next path node
- When reaching a node, current node should update
- Diagonal movement is not handled by MonsterBehaviour directly

The pathfinding system is responsible for deciding which nodes are included in the path.

---

# 5. MonsterBehaviour Movement Responsibilities

MonsterBehaviour should support:

1. Receiving a path
2. Storing the current path
3. Moving toward the next node position
4. Updating current node when a node is reached
5. Detecting arrival at the final target node
6. Stopping movement when no path is available

---

# 6. Required Runtime Fields

Recommended runtime fields:

| Field | Description |
|---|---|
| currentNode | Node currently occupied by the monster |
| targetNode | Final target node |
| currentPath | Current ordered path node list |
| pathIndex | Current index inside the path |
| isMoving | Whether the monster is currently moving |
| currentMoveSpeed | Runtime movement speed initialized from MonsterDefinition |
| arriveDistanceThreshold | Distance threshold used to determine node arrival |

---

# 7. Required APIs

Recommended APIs:

```csharp
void SetPath(List<NodeBehaviour> path)
```

Used to assign a new movement path to the monster.

```csharp
void SetTargetNode(NodeBehaviour targetNode)
```

Used to assign the monster final target node.

```csharp
NodeBehaviour GetCurrentNode()
```

Used by future dynamic path recalculation systems.

```csharp
void StopMovement()
```

Used by future death and target-arrival logic.

---

# 8. Movement Flow

Recommended movement flow:

```text
Monster receives path
→ Store path
→ Set pathIndex
→ Move toward next node
→ Reach node
→ Update currentNode
→ Move toward next node
→ Reach target node
→ Stop movement
```

---

# 9. Path Assignment Rules

When SetPath is called:

1. Validate path is not null
2. Validate path contains at least one node
3. Store path
4. Set pathIndex to the next movement target
5. Start movement

If path is invalid:

- Monster should stop movement
- No exception should be thrown during normal runtime

---

# 10. Current Node Tracking

MonsterBehaviour must track the current node.

Current node should update when the monster reaches a path node.

This is required for future dynamic path recalculation:

```text
Map walkability changes
→ MonsterManager asks monster for currentNode
→ Pathfinding recalculates from currentNode to targetNode
```

---

# 11. Target Arrival

When a monster reaches the final target node:

- Monster should stop movement
- Monster should notify a future manager or event hook if available
- Player damage handling is not implemented in this task

This task may expose a simple callback/event for future integration, but should not implement PlayerSystem logic.

---

# 12. Animation Rules

Monster movement should support basic walk animation triggering.

Recommended behavior:

- Use walkAnimationName from MonsterDefinition
- Avoid hardcoded animation state names
- Play walk animation when movement starts
- Stop or leave animation handling open when movement stops

This task does not implement hit animation or death animation behavior.

---

# 13. Spawn Integration

When monsters are spawned by MonsterSpawner:

1. MonsterSpawner instantiates monster prefab at Spawn Node position
2. MonsterBehaviour initializes from MonsterDefinition
3. MonsterBehaviour receives currentNode as Spawn Node
4. A path can be assigned from Spawn Node to Target Node
5. Monster starts movement along the assigned path

If MonsterSpawner does not yet assign paths, this task should expose the APIs required for later integration.

---

# 14. Out of Scope

The following systems are intentionally excluded from this task:

- A* pathfinding implementation
- Runtime path recalculation notifications
- Tower placement path validation
- Monster death flow
- Monster EXP reward flow
- Monster damage receiving logic
- Player damage system
- Battle victory or defeat conditions
- Crowd control effects

---

# 15. Acceptance Criteria

This task is considered complete when:

1. MonsterBehaviour can receive and store an ordered path.
2. MonsterBehaviour can move along path nodes.
3. Monster movement uses MonsterDefinition moveSpeed.
4. Monster moves from node center to node center.
5. Monster updates currentNode when reaching path nodes.
6. Monster can detect reaching the final target node.
7. Monster can stop movement safely.
8. MonsterBehaviour exposes currentNode for future dynamic path recalculation.
9. Basic walk animation can be triggered without hardcoded animation names.
10. No pathfinding algorithm, death logic, or player damage logic is implemented in this task.
